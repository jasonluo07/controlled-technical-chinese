# 範例

這個資料夾收集軟體規格與需求文件中常見、容易被誤讀的句子，並示範改寫的方式。規則從這些範例歸納出來。

## 每個範例的結構

| 段落 | 內容 |
|---|---|
| 改寫前 | 原本的寫法 |
| 問題 | 這句話可能有哪幾種讀法，或少了什麼資訊 |
| 本例的前提 | 改寫後用到、但改寫前沒有寫的所有資訊 |
| 本例不涵蓋 | 這個範例沒有處理的下一層問題，以及它在哪裡定義（只有部分範例有） |
| 改寫後 | 建議的寫法 |
| 重點 | 這個範例要說明的原則 |

## 已確認與待確認

改寫後能寫到多確定，取決於改寫的人手上的資訊有沒有依據。判斷的單位是**每一項資訊**，不是整個範例：

- **已確認的資訊**：改寫的人知道答案，例如作者本人，或已經向作者確認過。改寫後直接寫出答案，並在「本例的前提」列出這一項。
- **待確認的資訊**：改寫的人不知道答案。改寫後只寫原文已經確定的部分，把這一項列成「待確認」，並寫出要問作者的問題。

同一個範例可以同時有已確認和待確認的資訊。只要範例裡還有待確認的項目，標題就標註「（有待確認項目）」。所有資訊都待確認時，範例沒有「本例的前提」這一段。

「本例的前提」列出改寫後用到、但原文沒有的每一項資訊，包括選了哪一種讀法、新增的數字、位置、順序和介面文字。換一組前提，改寫後的內容也會不同。

不可以把猜測寫成已確定的內容。改寫的價值之一，就是讓缺口露出來。

### 預設的動作者

改寫後的「系統」指規格所描述的軟體整體。原文沒有寫出動作者時，只有在下列條件都成立時，改寫後才可以寫成「系統」，不必列進「本例的前提」：

- 依改寫前的文字和已經寫明的上下文，可以排除由人執行的讀法。注意：使用者透過介面操作時，動作也由軟體完成，但仍然是由人觸發的動作。
- 不需要指出由軟體的哪一部分執行。

不可以因為改寫後採用了自動執行的做法，就反過來認定原文只有這一種讀法。無法排除由人執行的讀法時，把動作者列進前提，或列成待確認。

下列情況仍然要把動作者列進前提：

- 這個動作可能由人執行，例如使用者、管理員、客服人員。
- 需要指出由軟體的哪一部分執行，例如伺服器、用戶端、後端。
- 範例要示範的問題就是動作者（C 類）。

### 待確認與待決

- **待確認**：改寫的人不知道答案是否已經有人決定。要問作者。
- **待決**：已經確認還沒有人決定。要由負責決定的人決定。

### 本例不涵蓋

有些範例碰到的下一層問題，屬於另一個主題，無法在同一個範例裡寫完，例如效能驗收環境的建置。這時在範例結尾加「本例不涵蓋」一段，寫出：

- 沒有涵蓋的是哪一層。
- 這一層要在哪裡定義，例如另一份文件或另一個範例。

「本例不涵蓋」只用在另一個主題上。範例本身要示範的問題，必須在範例裡寫完。

## 其他說明

- 範例改編自真實的軟體規格。產品名稱、功能和數字都已換成通用情境，只保留句子本身的問題。
- 「本例的前提」裡的具體數字（例如「30 天」「2 MiB」）是示意。實際的值由需求方決定。
- 改寫後如果引用介面上的文字（例如錯誤訊息），引號內的文字不受這份規範的用詞限制。介面文案有自己的寫作慣例。
- 每個範例只示範一個語言問題。改寫後碰到另一類問題時，以前提交代，或引用另一個範例（例如「字元的計算方式見 Q1」）。
- 分類之間有重疊，同一個句子常常同時有好幾種問題。範例放在最主要的那一類。
